# Configuration

Codee works with tasks providers to execute them. After you run `uv run codee-start` you need to open Codee UI and open `Settings`.

:::tip

`uvx codee-agent init` asks for most of this in the terminal — the coding agent, the max
parallel tasks, and, for Jira, every credential below. See [Installation](./installation).
This page is where you change any of it afterwards, and where Azure DevOps is connected.

:::

## Coding agent configuration

Codee supports Claude Code and Github Copilot coding agents. You need to select one of them.

### Max parallel tasks

Codee can execute multiple tasks in parallel. Specify number of parallel tasks here.

## Tasks provider configuration

Jira and Azure Dev Ops currently supported. Choose one of them.

### Jira settings

For Codee in Jira you need to create a separate user account. So it acts as a real user.

#### Base URL

Your Jira domain, e.g. `https://myjira.atlassian.net`.

#### API Token Owner Email

The email the API token below belongs to. Jira Cloud's REST API authenticates with HTTP
Basic where the username is that email, so it is required — but it is only a credential.
It does not decide which issues Codee picks up: the poll does not filter on an assignee,
only on the project, the work item types and the statuses the skills trigger on.

#### API token

API token to access Jira. Create a separate API token in Codee account settings.

#### Project key

The short prefix on every issue key in the project, **not the project's name** — for issue
`MYPRJ-4124` the project key is `MYPRJ`. Jira shows it under **Project settings → Details**,
and it appears in the URL of any board. Codee polls this one project only.

### Azure DevOps

For Azure DevOps you will need to create an App Registration,  you will see instruction on the Settings page on how to do that.

As with Jira, the connected account is a credential and a scope, not a filter: the poll
does not look at who a work item is assigned to, only at the work item types, the states
the skills trigger on, and the projects that account can read.

#### Organization URL

Specify your organiztion URL in Azure DevOps.

After you specified Organization URL fill in fields based on app registration:

- Application (client) ID
- Client secret
- Directory (tenant) ID (optional)

Then click Connect to Azure DevOps. You will have to grant access for your app and after that the setup is done.

### Work items

Codee only picks up work items whose type you have listed here. Every row maps one of
Codee's work items — the name a skill declares in `x-codee-issue-type` — to what your
provider calls it.

`story` and `task` are always present and cannot be removed: the skills that ship with
Codee trigger on them, and a story is what tells Codee to drive its children inside the
story's own run rather than one by one. Their provider type is yours to change. Out of the
box they point at:

| Codee work item | Jira | Azure DevOps |
| --- | --- | --- |
| `story` | `Story` | `User Story` |
| `task` | `Task` | `Task` |

**Load types from provider** fills the dropdowns with the types your backend actually
defines — the issue types of the configured Jira project, or the work item types across
your Azure DevOps organization's projects. It needs the credentials above to be filled in
(and, for Azure DevOps, connected), but nothing has to be saved first.

Use **Add work item** for anything beyond a story and a task — a `bug` pointed at your
backend's `Bug`, say. A skill can then declare `x-codee-issue-type: bug`, and the Workflow
page gets its own graph for it.

A work item whose type is not listed here is left alone, whatever state it is in.

### Custom JQL / WIQL

An optional extra condition every task query is narrowed by, written in the selected
provider's own query language — JQL for Jira, WIQL for Azure DevOps. It is empty out of
the box, and while it stays empty the poll is exactly the one described above.

When you fill it in, it is added to every fetch as one more `AND` condition on top of the
work items and the statuses your skills trigger on — it can only narrow what Codee picks
up, never widen it. Write the condition alone; a leading `AND` is dropped for you, and the
whole clause is bracketed before it is joined, so an `OR` inside it stays inside it.

| Provider | Example |
| --- | --- |
| Jira | `labels = "codee" AND component != "legacy"` |
| Azure DevOps | `[System.Tags] CONTAINS 'codee'` |

This is also where an assignee filter goes. Codee does not apply one itself — status and
type are the whole handover — so a team that wants "only what is assigned to Codee" writes
it here: `assignee = "codee@yourcompany.com"` for Jira, `[System.AssignedTo] = @Me` for
Azure DevOps, where `@Me` is the account that authorized the connection.

Each provider keeps its own filter, so switching provider and back does not lose it.
Nothing is validated as you type: the backend is the only thing that can say whether a
clause parses, so use **Verify connection** below to have it checked — an invalid filter
fails there with the message the provider returned, rather than silently returning no
tasks on every poll.

### Verify connection

Once every field of the selected provider is filled in (and, for Azure DevOps, the app is connected), a **Verify connection** button becomes available at the bottom of the Tasks provider section.

Clicking it pulls tasks exactly the way Codee does when it polls: same account, same work item types, same statuses your issue-triggered skills declare, and the same custom filter if you set one. It reports either the tasks it found or the reason the provider refused — a wrong project key, an expired token, an unreachable host. Nothing is saved by verifying, so you can check credentials before storing them.

### Setting up MCP server for tasks provider

When you have set up a task provider you will have button `Setup MCP Server` activated. In order to work for Codee you should also click
this button. That will configure mcp server for the selected provider in `.mcp.json` file.

### Verifiying tasks provider connection

You can verify task provider / its MCP are working by clicking Verify connection button. It will try to fetch, create, update tasks.
